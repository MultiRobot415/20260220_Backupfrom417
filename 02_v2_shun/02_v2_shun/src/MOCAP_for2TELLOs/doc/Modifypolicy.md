## 問題の概要

### 現象

- 故障注入（Fキー）時にオブザーバーの残差が期待通り増大しない
- 信頼度が十分に低下せず、リーダー交代が発動しない
- 残差ノルムが故障検知閾値（0.3m）を超えない

### 期待される動作

```
正常時: オブザーバー予測 ≈ 実際の位置 → 残差小
故障時: オブザーバー予測 ≠ 実際の位置 → 残差大 → 信頼度低下 → リーダー交代
```

### 実際の動作

```
正常時: 残差小 ✅
故障時: 残差小 ❌（問題）
```

## 根本原因の分析

詳細なコード分析の結果、**3つの重大な設計上の問題**を特定しました。

---

### 問題1: 制御入力モデルの影響が極端に小さい ⚠️ 最重要

#### 現在の実装（`observer.py` 84-107行目）

```python
def _rc_to_acceleration(self, rc_command: np.ndarray) -> np.ndarray:
    roll_cmd, pitch_cmd, throttle_cmd, yaw_cmd = rc_command
    
    # 現在のスケーリング係数
    ax = -pitch_cmd / 10.0  # 前進（+pitch）で+x方向の加速度
    ay = roll_cmd / 10.0    # 右傾斜（+roll）で+y方向の加速度
    az = throttle_cmd / 10.0 # +throttleで+z方向（上向き）の加速度
    
    return np.array([ax, ay, az])
```

#### 問題の定量的分析

| パラメータ | 値 | 説明 |
|----------|-----|------|
| RC値の範囲 | ±20 | 制御値の制限範囲 |
| スケーリング係数 | `/10.0` | RC値→加速度の変換係数 |
| 加速度 | ±2.0 m/s² | `20 / 10.0 = 2.0` |
| サンプリング時間 | 0.1秒 | 制御ループ周期 |
| **速度への影響** | **±0.2 m/s** | `2.0 * 0.1 = 0.2` |
| **位置への影響** | **±0.02 m** | `0.2 * 0.1 = 0.02` |

#### 故障検知への影響

```python
# 故障検知閾値
self.fault_threshold = 0.3  # 30cm
```

**制御入力の1サイクル影響: 0.02m（2cm）**  
**故障検知閾値: 0.3m（30cm）**  
**比率: 2cm / 30cm = 1/15**

**結論**: 制御入力の影響が閾値の1/15程度しかないため、故障注入しても残差が閾値を超えません。

#### なぜこの問題が発生するか

オブザーバーの予測ステップ（`observer.py` 109-130行目）：

```python
def predict(self, control_input: np.ndarray = None) -> np.ndarray:
    # 基本的な状態遷移
    self.x_hat = self.A @ self.x_hat
    
    # 制御入力がある場合、その効果を加味
    if control_input is not None:
        acceleration = self._rc_to_acceleration(control_input)
        # 速度成分に加速度を適用
        self.x_hat[3:6] += acceleration * self.dt  # ← 影響が極小
    
    return self.x_hat[:3]
```

**制御入力の影響が極めて小さいため、オブザーバーは実質的に制御入力を無視して動作しています。**

### 問題2: 座標系の不一致 ⚠️ 重要

#### システムの座標系（`README.md` 143-146行目）

```
X軸: 前後方向（+X=前進、-X=後退）
Y軸: 上下方向（+Y=上昇、-Y=下降）
Z軸: 左右方向（+Z=右、-Z=左）
```

#### RC値の対応（Tello標準仕様）

```
rc_command = [roll, pitch, throttle, yaw]
- pitch    → X軸（前後）
- roll     → Z軸（左右）
- throttle → Y軸（上下）
```

#### オブザーバーの実装（`observer.py` 103-105行目）

```python
ax = -pitch_cmd / 10.0  # pitch → X軸 ✅ 正しい
ay = roll_cmd / 10.0    # roll → Y軸 ❌ 間違い（本来はZ軸）
az = throttle_cmd / 10.0 # throttle → Z軸 ❌ 間違い（本来はY軸）
```

#### 問題点

**Y軸とZ軸が逆になっています。**

これにより：
- 上下方向の制御入力が左右方向の加速度として扱われる
- 左右方向の制御入力が上下方向の加速度として扱われる
- 故障検知が正しく機能しない

---

### 問題3: オブザーバーゲインが過度に大きい ⚠️ 中程度

#### 現在の設定（`observer.py` 48-55行目）

```python
self.L = np.array([
    [1.5, 0, 0],  # 位置フィードバックゲイン
    [0, 1.5, 0],
    [0, 0, 1.5],
    [0.6, 0, 0],  # 速度フィードバックゲイン
    [0, 0.6, 0],
    [0, 0, 0.6]
])
```

#### 問題の定量的分析

オブザーバーの更新式（`observer.py` 176-177行目）：

```python
# 状態の更新
self.x_hat = self.x_hat + (self.L @ self.residual).flatten()
```

**残差が0.3mの場合の位置補正量**:
```
補正量 = L_position * residual = 1.5 * 0.3 = 0.45m
```

**1サイクル（0.1秒）で45cmも補正されます。**

#### 問題点

位置フィードバックゲイン`L = 1.5`が大きすぎるため：

1. オブザーバーが測定値に過度に追従する
2. 制御入力による予測の影響が打ち消される
3. 残差が急速に減少し、故障検知が困難になる

#### 理論的背景

ルーエンバーガーオブザーバーの設計原則：

```
大きいゲイン → 速い収束、測定値への追従 → 制御入力の影響が小さい
小さいゲイン → 遅い収束、制御入力の影響が大きい → 故障検知に有利
```

**現在の設定は「速い収束」を重視しすぎており、故障検知には不利です。**

## 修正方針

### 基本方針

1. **制御入力の影響を適切なスケールに調整**（問題1の解決）
2. **座標系を統一**（問題2の解決）
3. **オブザーバーゲインを適切に調整**（問題3の解決）
4. **故障検知閾値の見直し**（オプション）

### 設計思想

```
オブザーバーの役割:
- 正常モデルに基づいて状態を推定
- 実際の動作との乖離（残差）から故障を検知

重要な原則:
- 制御入力の影響を適切にモデル化
- 測定値への過度な追従を避ける
- 故障時に残差が明確に増大するように設計
```

```python
def _rc_to_acceleration(self, rc_command: np.ndarray) -> np.ndarray:
    if rc_command is None:
        return np.zeros(3)
        
    roll_cmd, pitch_cmd, throttle_cmd, yaw_cmd = rc_command

    ax = -pitch_cmd / 10.0  # 前進（+pitch）で+x方向の加速度

```

#### 修正後

```python
def _rc_to_acceleration(self, rc_command: np.ndarray) -> np.ndarray:
    """
    RCコマンドから予想される加速度を計算
    
    Args:
        rc_command: [roll, pitch, throttle, yaw]のRCコマンド
        
    Returns:
        予測される加速度 [ax, ay, az]
        
    修正内容:
        - スケーリング係数を10.0から40.0に変更（4倍）
        - 座標系を修正（Y軸とZ軸の対応を修正）
        - RC値20で約0.5m/s²の加速度（実機特性に基づく）
    """
    if rc_command is None:
        return np.zeros(3)
        
    roll_cmd, pitch_cmd, throttle_cmd, yaw_cmd = rc_command
    
    # 適切なスケーリング係数（RC値20で約0.5m/s²の加速度）
    # 係数を10.0から40.0に変更（4倍）
    # 座標系を修正: throttle→Y軸、roll→Z軸
    ax = -pitch_cmd / 40.0    # pitch → X軸（前後）
    ay = throttle_cmd / 40.0  # throttle → Y軸（上下）← 修正
    az = roll_cmd / 40.0      # roll → Z軸（左右）← 修正
    
    return np.array([ax, ay, az])
```

#### 修正の効果

| 項目 | 修正前 | 修正後 | 改善率 |
|-----|--------|--------|--------|
| スケーリング係数 | `/10.0` | `/40.0` | - |
| RC値20での加速度 | 2.0 m/s² | 0.5 m/s² | 実機特性に適合 |
| 1サイクル速度変化 | 0.2 m/s | 0.05 m/s | 適切 |
| 1サイクル位置変化 | 0.02 m | 0.005 m | 適切 |
| 10サイクル累積影響 | 0.2 m | 0.05 m | 適切 |
| 座標系 | Y/Z逆 | 正しい | ✅ |

**注**: スケーリング係数を小さくすることで、制御入力の影響は控えめになりますが、累積効果により故障検知には十分です。

## 注意事項

### 1. スケーリング係数の調整について

本修正案では`/40.0`を提案していますが、実機の動特性により最適値は異なる可能性があります。

**調整の指針**:
- 係数を小さくする（例: `/30.0`）→ 制御入力の影響が大きくなる
- 係数を大きくする（例: `/50.0`）→ 制御入力の影響が小さくなる

**推奨アプローチ**:
1. まず`/40.0`で実装
2. 実機テストで残差の挙動を確認
3. 必要に応じて微調整

### 2. オブザーバーゲインの調整について

ゲインを小さくすると：
- **メリット**: 故障検知性能が向上
- **デメリット**: 収束が遅くなる、ノイズの影響を受けやすい

**推奨アプローチ**:
1. まず提案値（0.8, 0.4）で実装
2. 正常時の安定性を確認
3. 故障検知性能を確認
4. トレードオフを考慮して最終調整

### 3. 段階的な実装

一度にすべての修正を実装するのではなく：

1. **フェーズ1**: 修正1（スケーリング係数）のみ実装 → テスト
2. **フェーズ2**: 修正2（座標系）を追加 → テスト
3. **フェーズ3**: 修正3（ゲイン）を追加 → テスト
4. **フェーズ4**: 必要に応じて閾値調整

各フェーズで効果を確認することで、問題の切り分けが容易になります。

## まとめ

故障検知時に残差が大きくならない問題は、**制御入力モデルのスケーリング係数が不適切**であることが根本原因です。

**重要な修正**:
1. スケーリング係数を`/10.0`から`/40.0`に変更
2. 座標系を修正（Y軸とZ軸の対応）
3. オブザーバーゲインを調整（故障検知重視）

これらの修正により、故障注入時に残差が適切に増大し、信頼度ベースのリーダー交代機能が正常に動作することが期待されます。
